# App credential onboarding

Use this workflow only when an Android sender integration has no reusable App ID and SDK App Secret. Before invoking it, inspect an existing project's `setSdkInitInfo` arguments and credential source as described in [incremental integration](incremental-integration.md). If both arguments are non-placeholder values, preserve them and do not run registration, login, or this onboarding script. For a project using credentials generated by this Skill, use the read-only check before every Debug and Release build. The detected package is authoritative; display it, but do not ask the developer to confirm it again.

## Preparation

Collect the Android project root and application name. The script reads the literal `applicationId` from the module applying `com.android.application`; do not ask the developer to type it again. If the project has multiple application modules, select the intended one with `--module-dir`. Do not ask for or validate a distribution channel before registration: the script uses the stable built-in `src` value `android-sender-sdk`. The developer needs access to an 11-digit mobile number and its SMS messages.

Do not ask the developer to paste a mobile number, password, verification code, token, App Secret, or md5Key into chat. Run the script from the current Skill session; do not open or ask the developer to open another terminal. The script first opens a modal input dialog for the mobile number, verification code, new password, password re-entry, and multi-account selection. Every dialog title, guidance message, validation error, and retry prompt shows Chinese first and English second; macOS and Windows buttons are bilingual, and Linux uses bilingual button labels when its dialog backend supports them. On Windows it uses the system Windows PowerShell and WinForms; on macOS it uses `osascript`; on Linux it uses `zenity` or `kdialog`. Tk is the graphical fallback. If the graphical backends are unavailable, continue in the terminal with the same bilingual prompts: ordinary fields use normal input, while verification-code and password fields first use hidden `getpass` input. If the terminal cannot disable echo, show a bilingual warning that the next value will be visible, then continue with ordinary terminal input. The script does not repeat the entered value afterward and keeps sensitive values out of command-line arguments and application logs.

When registration needs a new account password, the password dialog tells the developer that the mobile number entered earlier is the platform username and that they must remember both the username and password. They may be required to sign in with them later to change application information. The reminder appears before password entry without printing either credential. Password re-entry uses a second masked dialog to validate the typed value; it is not an approval confirmation.

## Registration and login state machine

Do not add a separate account-status request or password-login request. For a mobile number that is not known locally as registered, the script sends one SMS, collects one verification code, collects the new-account password required by the registration request, and calls `/auth/skill/register`. The registration endpoint makes the account-existence decision. A successful response completes registration. Error `1101` means the mobile number was already registered: discard the proposed registration password and immediately call `/auth/skill/login` with the same mobile number and the same verification code. Do not send a second SMS and do not ask for the code again during this transition.

The first login request uses `mobile` and `code`, not the platform password. If it returns `1103`, show the returned `accountList`, let the user select an account, then call the same login endpoint with `mobile`, the selected `account`, and `identity`. If login returns `1105`, return to registration at most once; a second register-to-login-to-register contradiction stops onboarding. Error `1104` or an expired code starts a fresh SMS cycle as required by the platform contract.

Locally cached `registered` state can skip the initial registration attempt only when its saved mobile number exactly matches the newly entered mobile number. When the entered number changes, clear the cached account authentication state before saving the new number. A different mobile number always starts from registration, including after a failed or interrupted run, so stale state cannot route the wrong account directly to login.

## Run

For a new integration or an existing integration already using this Skill's credential format, validate the destination and generated credential mapping without making network requests. Do not run this command merely because a host-managed integration lacks `local.properties` keys or `SkillSdkConfig`; first reuse its existing initialization credential pair. Before first onboarding, the check reports that complete Skill-managed credentials are absent; continue with mutating onboarding only when no reusable host-managed pair exists:

```bash
python3 scripts/onboard.py \
  --project-dir /path/to/android-project \
  --app-name "Example App" \
  --check
```

If the existing project has one unambiguous application module, continue without asking the user to reconfirm its detected `applicationId`. If multiple application modules exist, ask only which module is the target. When neither reusable host-managed credentials nor complete Skill-managed credentials exist, run the mutating onboarding mode with `--confirm`:

```bash
python3 scripts/onboard.py \
  --project-dir /path/to/android-project \
  --app-name "Example App" \
  --confirm
```

`--src <value>` remains available only as an optional caller override. Its absence must never block onboarding.

The script always uses the production platform at `https://openplat.hpplay.cn`; it has no production/test command-line option. It displays the endpoint, application name, and detected package. Mutating onboarding sends the SMS, registers or authenticates the account, and then calls the idempotent application-creation endpoint, which returns existing credentials when the same accessible package is already registered.

After successful registration, credentials are written to the project's `local.properties` using these keys:

```properties
hpplay.appId=...
hpplay.appSecret=...
hpplay.md5Key=...
```

The script skips network onboarding when all three values already exist. It removes the obsolete `hpplay.environment` property when writing newly obtained credentials. For these Skill-managed credentials, run the read-only `--check` before every Debug and Release build. When complete credentials exist, the check must validate the generated config and print `SDK credential mapping is valid: APP_SECRET uses platform md5Key.` A missing, stale, or manually changed generated config makes the check fail and must block the build until onboarding regenerates it. This requirement does not migrate a pre-existing host-managed pair into the Skill format.

The fields have distinct roles: `hpplay.appSecret` preserves the platform response's `secret`, while `hpplay.md5Key` preserves its `md5Key`. The Android sender SDK uses `md5Key` as the secret argument during initialization.

The script also generates an ignored Java source file at `<application-module>/src/main/java/<applicationId>/SkillSdkConfig.java`:

```java
SkillSdkConfig.APP_ID
SkillSdkConfig.APP_SECRET
```

This mapping is invariant: `APP_ID = hpplay.appId` and `APP_SECRET = hpplay.md5Key`. `APP_SECRET` must never use `hpplay.appSecret`, because the SDK initialization argument named `appSecret` actually expects the platform `md5Key`. The generator writes that warning into `SkillSdkConfig.java` and verifies both assignments immediately after writing. Use these constants from the SDK initialization code and continue the integration in the same Skill session. The generated file is project code for local compilation, but is automatically added to `.gitignore` because it contains credentials.

The script refuses to write to a Git-tracked or non-ignored project file. `create_android_project.py --confirm` initializes its new project with `git init`, and its `.gitignore` already covers `local.properties`. For a manually created project that is not in Git, either initialize Git and verify the credential destination is ignored, or use `--credentials-file /external/path/hpplay.properties`; do not rerun onboarding unchanged after the Git safety error. The credential file is written with user-only permissions. Resumable account state is stored under the user's platform state directory, not in the project; `--reset-state` removes it before a run. The authentication flow first opens the mobile-number dialog as data entry and falls back to terminal input if graphical input is unavailable; it does not ask a late `[y/n]` question about reusing a saved number.

Every invocation requires both `--project-dir` and `--app-name`, including `--check`. Do not use the shorthand `scripts/onboard.py --check` or `scripts/onboard.py --confirm`; argparse rejects it before project detection.

After onboarding, use the generated `SkillSdkConfig` constants in SDK initialization:

```java
sdk.setSdkInitInfo(context, SkillSdkConfig.APP_ID, SkillSdkConfig.APP_SECRET).bindSdk();
```

Keep both the raw platform `secret` and `md5Key` in the ignored local properties file. Platform `secret` is storage-only for workflows that explicitly require that platform field: never pass it to `setSdkInitInfo`, write it to `SkillSdkConfig.APP_SECRET`, substitute it manually, or print or commit either value.

## Recovery

The script handles an existing account, multi-account selection, expired verification sessions, expired tokens, an existing package application, and one permitted rate-limit retry. It stops instead of looping when registration and login disagree repeatedly.

For an application-limit error, reuse an existing App ID or remove an unused application in the console. If the package belongs to an application the current account cannot view, contact the tenant administrator or change the package; do not retry the same package and do not send the developer to registration.

For other unrecoverable failures, the script prints the production-platform browser onboarding link. Continue after the developer completes that flow and provides credentials through a secure local mechanism. Never place real credentials in the Skill package.

Keep the production hostname fixed in the distributed Skill. Do not add a runtime production/test selector or allow test credentials and cached authentication state to cross environments.
