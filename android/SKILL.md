# Android Sender SDK Integration

Use the SDK API shipped with the target SDK version as the source of truth. Resolve all references relative to this file. If an API name differs in the installed SDK, inspect its public interfaces before editing the host app.

## Workflow

1. Start with [project setup](references/project-setup.md). Detect an existing Android application project and use it when present. An empty current working directory is automatically the new-project destination; do not ask the user to provide a path. If no application project exists, the next user-facing prompt must be the application-name numbered menu shown below. Do not ask an open question, do not say `请提供应用名称和 applicationId`, and do not request both values together. Resolve and validate the application name first; only after the user selects it, show the separate `applicationId` numbered menu. Each menu has two concrete candidates and a final `自己输入` item. Free text is accepted only after the user selects `自己输入`. After both values are valid, show the pair once and ask the `[y/n]` creation confirmation. Only `y` may create the project with `--confirm`; `n` returns to value selection. Do not silently select or timeout-default identity values. If multiple application modules exist, have the user select the target module before continuing.
2. Before running setup or onboarding, inspect the selected project and classify the request as a new/full integration or an incremental capability change. Read [incremental integration](references/incremental-integration.md) when the project already contains the sender SDK dependency, SDK initialization, or casting code. Reuse its SDK artifact, application identity, credentials, coordinator, discovery, and connection flow. The absence of Skill-managed `local.properties` entries or `SkillSdkConfig` is not evidence that an existing integration lacks credentials.
3. For a new/full integration, run all read-only preflight checks before implementation: `scripts/prepare_android_env.py --project-dir <project> --check`, `scripts/obtain_sdk_aar.py --project-dir <project> --check`, and `scripts/onboard.py --project-dir <project> --app-name "<application name>" --check` when the credentials are Skill-managed or no reusable credential source exists. Both onboarding arguments are mandatory; never abbreviate that invocation to `scripts/onboard.py --check`. Skip onboarding checks for a reusable host-managed pair. For an incremental change, run only the checks relevant to the requested capability; do not reacquire an already integrated SDK or invoke onboarding for an existing non-placeholder App ID and SDK App Secret. Do not modify the project, accept licenses, install tools, install the AAR, send SMS, authenticate, or create an application while these checks are being reviewed.
4. Resolve the Android SDK license `[y/n]` when applicable. An existing project's detected `applicationId` is authoritative; display it but do not ask the user to confirm it again. A new project's application name and `applicationId` were already confirmed during project creation and must not trigger a second confirmation during onboarding. If the user explicitly requested media push, real-time screen mirroring, or adding one of them to an existing integration, that request determines the target scope and no casting-scope menu is shown. Show the numbered menu `1. 仅媒体推送（默认）`, `2. 仅手机屏幕实时镜像`, `3. 媒体推送 + 手机屏幕实时镜像` only for a new/full integration whose requested scope remains ambiguous. This selection is not an approval confirmation and therefore does not use `y/n`. It alone has a 30-second timeout, treated as `1`; tell the user that the default was selected. After this phase, do not ask for another approval confirmation during SDK integration.
5. Read [build environment](references/environment-setup.md), then prepare missing tools only after the preflight decisions are complete. Do not require the developer to install JDK, Android SDK, `adb`, or global Gradle first. Carry the selected environment into every Gradle command.
6. Read [SDK AAR acquisition](references/sdk-artifact.md) only when the SDK artifact is absent or the user requested an update, then install the checked official AAR from the Skill's fixed HTTPS CDN URL. Do not replace a working existing artifact merely because the request adds another casting capability, and do not ask the developer to provide an AAR.
7. Read [API reference](references/api-reference.md) for the selected workflow. For every integration that discovers or connects devices, read [discovery and connection](references/discovery-connection.md); implement it for a new integration, or preserve and extend the existing long-lived coordinator for an incremental change. Read [SDK installation](references/sdk-installation.md) for Gradle, AndroidX Core, application icon, repository access, permissions, lifecycle, manifest merging, and packaging details. The local AAR does not publish its `androidx.core` dependency transitively, so the host must add it explicitly before any mirror flow is tested. For screen mirroring from an ordinary application, keep `LelinkPlayerInfo.useSystemMirrorCapture` at its default `false` value and use the normal MediaProjection consent flow; never set it to `true` merely to avoid or simplify permission handling. The host application's `<application>` must explicitly set `android:usesCleartextTraffic="true"` and a valid `android:icon`. Use [API contract](references/api-contract.md) as the short checklist.
8. Reuse credentials when the project already passes a non-placeholder App ID and SDK App Secret to `setSdkInitInfo`, whether they come from `SkillSdkConfig`, `BuildConfig`, resources, or another existing local configuration. Do not print or migrate their values, and do not run mutating onboarding. Run `scripts/onboard.py --project-dir <project> --app-name "<application name>" --confirm` only when no reusable credential pair exists and the required preflight has completed. Follow [credential onboarding](references/onboarding.md). For Skill-generated credentials, the invariant is `SkillSdkConfig.APP_ID = appId` and `SkillSdkConfig.APP_SECRET = md5Key`; platform `secret` must never be passed to SDK initialization.
9. Check the actual API signatures and callback interfaces in the installed AAR. In particular, `ILelinkPlayerListener` has multiple required methods, and SDK binding completes asynchronously.
10. Put bind, browse, connection, selected-device, and connected-device state in one application-scoped or otherwise long-lived coordinator. Register callbacks before binding, preserve an existing credential source and `setSdkInitInfo(...).bindSdk()` call, and execute a pending browse request only after a successful bind callback. For Skill-generated credentials, `APP_ID` comes from platform `appId` and `APP_SECRET` comes from platform `md5Key`, not platform `secret`. Keep the exact current `LelinkServiceInfo` selected from the latest browse or parse callback and pass it to `connect()`; do not recreate a device from name, IP, or cached display fields. Process every browse callback but coalesce identical diagnostic/UI emissions using a stable device-content fingerprint. Treat connection as successful only in `IConnectListener.onConnect`, and start casting only with that connected device.
11. Handle the separate search, parsing, connection, and player callback domains according to [error handling](references/error-handling.md). Show the SDK's installation guide for an unsupported sink; give network troubleshooting for a search with no device responses.
12. Before showing controls, query `queryCastCapability()` after the current cast starts. Use SDK capability checks for optional list controls. For cross-network media, supply a receiver-accessible HTTP(S) URL.
13. Immediately before every Debug and Release build, rerun `scripts/onboard.py --project-dir <project> --app-name "<application name>" --check` only for Skill-managed credentials and require `SDK credential mapping is valid: APP_SECRET uses platform md5Key.` For a pre-existing host-managed credential pair, preserve its source and verify that the final build still supplies both initialization arguments without printing them; do not force migration into the Skill's onboarding format. Inspect each variant's final merged Manifest and require `android:usesCleartextTraffic="true"`, a valid application icon, and `android.hardware.usb.host` with `android:required="false"`; review every permission and component merged from the AAR against the selected product capabilities and privacy declaration. Verify the builds, binding, discovery, connection, requested casting modes, callbacks, lifecycle transitions, and Release/R8 behavior using [acceptance guidance](references/acceptance.md). A compiled APK is not sufficient: exercise mirroring through foreground-service startup and capture distinct browse/player state transitions without flooding logs with identical callbacks. State what remains unverified without devices or service credentials.

## Required Empty-Directory Prompt

When the current directory is empty, stop after presenting this first menu and wait for one selection:

```text
请选择应用名称（输入序号）：
1. 投屏助手（推荐）
2. Sender SDK Test
3. 自己输入
```

If the request already supplies an application name, put that value at option `1` and retain two other options. After the application name is selected, present `applicationId` candidates in a separate turn, for example:

```text
请选择 applicationId（输入序号）：
1. com.example.castsender（推荐）
2. com.example.hpplay.sender
3. 自己输入
```

Never replace either menu with a request to provide values. Do not show the second menu before the first selection is known.

## Important Boundaries

- Every binary confirmation shown by the Skill must use `[y/n]` and accept only case-insensitive `y` or `n`. `y` confirms and permits the guarded action; `n` rejects it. Reprompt after empty or any other input, and never interpret silence as `y`. Casting scope is a three-item numbered value selection rather than a binary confirmation; show it only when a new/full integration remains ambiguous, never when the user explicitly requested a capability or an incremental addition. It is the only timed prompt and treats its 30-second timeout as option `1`. Ordinary data entry (including mobile number, verification code, password, password re-entry, and account selection) is collected through a modal input dialog when available, with terminal fallback when unavailable; terminal verification-code and password fields first use hidden `getpass` input, then continue visibly after a warning only if echo cannot be disabled.
- Do not expose passwords, verification codes, tokens, platform `secret`, or `md5Key` in command-line arguments, chat, logs, or diagnostic uploads. The generated local SDK config contains `appId` and the SDK credential derived from `md5Key`, and must remain ignored by Git.
- Do not treat missing Skill-managed credential files as permission to register or log in when the existing project already supplies a non-placeholder App ID and SDK App Secret. Preserve host-managed credentials in place. For Skill-generated credentials, the mapping is non-negotiable: `SkillSdkConfig.APP_ID` uses platform `appId`, and `SkillSdkConfig.APP_SECRET` uses platform `md5Key`. Never use platform `secret` for SDK initialization. A missing, stale, or manually changed generated config must fail onboarding preflight and block the build until onboarding regenerates it.
- Cleartext LAN metadata access is required: every integrated host app must declare `android:usesCleartextTraffic="true"` on `<application>`. If the app also uses `android:networkSecurityConfig`, that configuration must permit cleartext traffic too. The SDK queries a receiver's dynamic private-IP HTTP `DnsTxtInfo` endpoint; without an effective allow policy Android can block the request, leave the receiver App ID empty, and cause a false `212010/212101` not-official-sink result.
- Do not accept Android SDK licenses on the developer's behalf or place machine-specific JDK/SDK paths in tracked files.
- Do not overwrite an existing project. The managed `libs/android-sender-sdk.aar` is updated automatically when the official CDN publishes a different artifact.
- A local AAR cannot carry Maven transitive dependencies. Every host must include `androidx.core:core` explicitly because the SDK's capture permission page uses `ContextCompat` and its mirror notification uses `NotificationCompat`. Every host must also supply a non-zero application icon usable by the mirror foreground notification; compilation alone does not validate either requirement.
- Treat every host as an ordinary third-party application unless the user explicitly identifies it as a system application and project evidence confirms the SDK-supported system capture path. Ordinary applications must use MediaProjection for screen mirroring. Leave `LelinkPlayerInfo.useSystemMirrorCapture` unset (its default is `false`) or explicitly pass `false`; `useSystemMirrorCapture(true)` makes the SDK skip the ordinary MediaProjection authorization path and commonly causes mirroring to fail in a normal app. Do not infer system-capture eligibility from device ownership, platform signing alone, pre-granted runtime permissions, or a desire to suppress the consent dialog.
- Treat player callbacks as state notifications, not one-shot commands. `onStart` can repeat periodically during one media session, and a receiver may resume through `onStart` after `seekTo` without emitting `onSeekComplete`; initialize session resources elsewhere and confirm seek progress through position updates with a timeout.
- Keep SDK callbacks distinct: `IBrowseListener.onBrowse`, `IServiceInfoParseListener.onParseResult`, `IConnectListener.onDisconnect`, and `ILelinkPlayerListener.onError` carry different code domains.
- Do not call `stopBrowse()` merely because an Activity or Fragment receives `onPause()` or `onStop()`. Camera scanning, MediaProjection consent, permission screens, dialogs, and configuration changes can make the host UI transiently stop. Attach or detach UI observers there, but keep the SDK coordinator and active browse alive. Stop browsing only for an explicit user action, a controlled refresh/restart, or final coordinator teardown.
- Never collapse browse timeout, network loss, no-official-receiver, multicast-blocked, authentication failure, and parse failure into one empty-list state. Preserve and expose the callback domain and numeric code without logging credentials or QR/PIN contents.
- `diagnose()` is local-state text. Review it before uploading because it includes app ID and device information.
- The Skill-free sink check matches the discovered receiver App ID against channels whose server-side `type` is `1` (APK receiver). Treat it as the SDK's eligibility decision, not cryptographic proof of APK identity.
- Use [minimal examples](examples/README.md) as a starting point and adapt them to the host app's lifecycle.
